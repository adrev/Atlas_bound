# Atlas Bound Quality and Security Review

Review baseline: `5b0f2c6` (PR #204), September 7, 2026.

## Assessment

The game has a substantial feature set, useful shared rules utilities, and a
working automated baseline: 147 test files and 1,866 tests passed before edits.
The main remaining weakness is inconsistent authority. Some actions use guarded
database writes and filtered synchronization; older chat macros and parts of the
client still calculate and mutate the same resources independently.

This was a broad source review with targeted reproductions across login,
authorization, uploads, deployment, recovery, DDB imports, client targeting,
reconciliation, music, and encounter deployment. It is not a claim that every
line, D&D ability, or live multiplayer workflow was exhaustively tested.
Reproductions use current application code with controlled database, provider,
and network boundaries. No real OAuth identity or production data was modified.

## Fixes in This Branch

| Priority | Problem and player impact | Implemented correction |
| --- | --- | --- |
| P1 | An attacker could pre-register another person's email and inherit access when that person first signed in with OAuth. | New email links require a verified provider claim and a verified, passwordless existing identity. Local-password collisions stop with actionable login feedback. Existing provider IDs remain bound to their original accounts. |
| P1 | An unverified email matching the admin allowlist granted admin access. | Email-based admin matching requires the existing `auth_users.email_verified` field. Immutable user-ID matching still works. Google/Discord verified claims populate the field; untrusted claims do not. |
| P1 | Apple callback preferred browser-posted `user.email` over the token-endpoint email. | Only the token-endpoint identity can supply the account email and verification claim. |
| P1 | Encoded sibling paths could reach protected maps through the token-art exemption. | Decode and validate before namespace authorization; use the same authorized path for GCS and local static fallback. |
| P1 | Two mounted action panels both handled one target click. | One shared target dispatcher owns the event and rejects duplicate in-flight resolution. |
| P1 | A delayed session A snapshot could replace session B's characters/combat and advance B's cursor. | Fence snapshot/replay requests by session lifetime, including leaving and re-entering the same session. |
| P2 | Delayed replay could rewind tokens after a newer snapshot or live event. | Skip replay events already covered by the applied cursor; reject obsolete snapshots and stale conditional-response validators. |
| P2 | Rest calculations could overwrite a concurrent resource spend or character save. | Recovery writes compare the version read with the current database version. A conflict rolls back before any success event. Party recovery rolls back as a unit. |
| P2 | Recovery announced success even when no updated row/version was returned. | Require a confirmed newer version; otherwise roll back and tell the requester to refresh/retry. |
| P2 | Public rest summaries disclosed exact HP, resource counts, and concentration. | Keep detailed results in authorized character updates and requester-only responses. Public messages contain the action, not private sheet values. Targeted DM rests stay private. |
| P2 | Odd-level characters recovered too many Hit Dice; negative Constitution totals always healed at least 1 HP. | Recover half the total Hit Dice rounded down, minimum one. Hit Die healing can be zero. |
| P2 | Long rests refreshed dawn-only and manually managed feature charges. | Refresh only features explicitly marked for short/long rests. |
| P2 | A misspelled `!rest` command silently became a long rest; named targets could come from another map. | Validate the rest kind and resolve named tokens on the DM's viewed map. |
| P2 | DDB re-sync dropped `usesTotal`/`resetOn`, leaving spent resources unable to recover; aliases could duplicate reserved resources. | Preserve absent usage metadata and deduplicate reserved resource aliases without removing unrelated custom features. |
| P2 | Removed note authors could still edit/delete campaign notes. | Require current campaign membership before author/DM mutation rights. |
| P2 | Anonymous error throttling trusted a spoofable header and retained arbitrary IP keys indefinitely. | Use the configured trusted client IP and a bounded limiter with expiry. |
| P2 | Autoplay recovery started music at volume zero; stale fades/retries survived track changes. | Share the retry/fade initialization, read current volume, and cancel obsolete retries/fades on stop, mute, track change, and unmount. |
| P2 | A failed encounter HTTP response left Deploy permanently disabled. | Always clear the busy state and show an actionable failure message. |
| P2 | The locked dependencies accumulated five vulnerable packages, including build-only dependencies. | Apply compatible targeted updates for `qs`, both `fflate` branches, `@humanfs/node`, `browserslist`, and `nanoid`. Full audit is clean after the updates. |

The deployment recipe now caps the service at one instance. This is a temporary
mitigation for process-local room authority, not a distributed-state solution.
Live configuration has not been changed or verified by this review.

## Remaining Work, in Order

### 1. Make All HP Changes Use One Server Action Pipeline

Priority: P1. Owner: CodeX, beginning with Healing Light.
Tracked in [#206](https://github.com/adrev/Atlas_bound/issues/206).

Evidence: `server/src/services/chatCommands/subclassFeaturesTier10Handler.ts:208`,
`itemsTier20Handler.ts:46`, `spellsTier12Handler.ts:116`, and
`subclassFeaturesTier14Handler.ts:421` still contain direct HP updates, including
paths that swallow database failures. The shared combat service has stronger
guards that these paths bypass. The action panel also retains client-side
damage/resource resolution (`client/src/components/canvas/TokenActionPanel.tsx`).

Claude task: Route one action family at a time through a server service that
validates actor, target, turn, resources, and visibility. Commit resource spend
and healing/damage together; apply condition, concentration, death-save, and
Wild Shape side effects through the same result. Synchronize only committed
results, with a version. Keep explicit DM overrides separate and audited.

Acceptance: conflict, DB failure, repeated request, simultaneous action,
overhealing, temporary HP, unconscious target, and transformed target tests.
Neither a resource charge nor a success announcement may survive a failed action.

### 2. Bound Chronicle Generation and Make Job Creation Atomic

Priority: P1. Suggested owner: Fable, in a separate branch.
Tracked in [#205](https://github.com/adrev/Atlas_bound/issues/205).

Evidence: `server/src/routes/chronicle.ts:402` checks DM membership and transcript
length but lacks per-user budgets and concurrency limits. Creating one's own
campaign satisfies the DM check. `:437` allocates sequence numbers using
`MAX(...) + 1` outside a serialized transaction, despite the comment claiming
concurrent triggers cannot collide.

Claude task: Add durable user quotas, a per-campaign in-flight constraint, and
bounded worker concurrency. Allocate sequence numbers and enqueue the job in
one transaction. Apply equivalent controls to retry endpoints. Quota exhaustion
must return a useful status before making a model call.

Acceptance: hold one generation pending; repeated requests across the same
user's campaigns must not create excess jobs/provider calls. Test retries,
worker failure, expired jobs, and concurrent sequence allocation.

### 3. Persist the Remaining Class and Item Resource Pools

Priority: P2. Suggested owner: CodeX after the HP service slice.

Evidence: Healing Light uses `room.pointPools` and a free reset command in
`subclassFeaturesTier10Handler.ts:98`. Superiority Dice, Psi Warrior, Soulknife,
and magic-item pools remain process-local in `miscClassHandlers.ts`,
`subclassFeaturesTier14Handler.ts`, `subclassFeaturesTier15Handler.ts`, and
`itemsTier20Handler.ts`.

Claude task: Store distinct, versioned resources per character/feature or item
instance. Define class-level scaling, use limits, and recharge rules centrally.
Remove free player reset commands. Reuse the established Ki/Sorcery persistence
pattern, but avoid copying an entire command-specific implementation.

Acceptance: resources survive room eviction, restart, and DDB sync; two tabs
cannot double-spend; multiclass features with similar labels do not share pools.

### 4. Separate Pact Magic from Ordinary Spell Slots

Priority: P2. Suggested owner: CodeX; announce shared-type changes first.

Evidence: `server/src/services/RestService.ts:195` restores every slot whenever
the class string contains Warlock. The current slot model cannot distinguish
Pact Magic from a multiclass character's ordinary Spellcasting slots.

Claude task: Add explicit slot-pool identity and provenance across import,
storage, UI, spending, and recovery. Short rests recover Pact Magic only.
Also model temporary Flexible Casting slots, which currently cannot exceed
normal slot maxima. Design a backward-compatible migration before editing.

Acceptance: pure Warlock, Warlock/Wizard, and Warlock/Sorcerer recovery and
casting tests, including slot levels shared by both pools.

### 5. Finish Distributed Session Authority Before Scaling Up

Priority: P1 before more than one instance or overlapping revisions.
Tracked in [#207](https://github.com/adrev/Atlas_bound/issues/207).

Evidence: room roles, pending reactions, cursors, and action state are local
maps; role-changing routes update their own process. Session affinity does not
guarantee that REST and sockets reach the same instance.

Claude task: Choose one authoritative room owner or a shared state/command
service. Broadcast role/membership revocations across instances and recheck
privileged operations against authority. A Socket.IO adapter alone is not
enough: it shares broadcasts, not the mutable game state.

Acceptance: two real app instances against one database; demote, kick, ban,
leave, delete, and reconnect across instances. Old sockets must lose both
action permission and visibility. Include deployment-revision overlap.

### 6. Resolve Legacy Account Trust and Add Explicit Account Linking

Priority: P1 for suspicious historical mixed accounts; P2 for the linking UI.

The new guard stops future unsafe links. It cannot prove who created a
pre-existing password/OAuth combination. No historical password, session,
or provider link has been deleted in this patch.

Claude task: Audit mixed login accounts without exposing emails/hashes in
public issue logs. Design authenticated linking, mailbox verification, and
account recovery with credential/session revocation. Normalize local email
registration/login and plan case-insensitive uniqueness after reviewing
existing collisions. Do not auto-merge or delete accounts during migration.

Rollout: test the existing linked Google/Discord logins. An OAuth-only legacy
admin may need a fresh provider login to verify its email; a stable user-ID
allowlist entry avoids that dependency.

### 7. Make Encounter Deployment a Server Transaction

Priority: P2. Suggested owner: Fable after the Chronicle work.

Evidence: `client/src/components/dm/EncounterBuilder.tsx` creates character rows
one by one, then emits token-add events. Some failures silently fall back to
tokens without characters; partial retries can duplicate already-spawned
creatures. The button retry fix does not make this operation atomic.

Claude task: Send preset, map, zone, and idempotency key to one authorized
server endpoint. Validate the full encounter and spawn character/token rows
transactionally. Return committed IDs and synchronize once. Fence map/session
changes during the request.

Acceptance: mid-batch failure leaves no partial encounter; retry does not
duplicate; missing monsters produce a useful error; token size and zone bounds
are respected.

## Structure and Product Improvements

- Break up the 6,021-line action panel by action family. UI components should
  collect intent and display results; server services should own rules and
  writes. The duplicate target handler was a concrete symptom of combining
  presentation and execution in several mounted surfaces.
- Replace numbered chat-handler tiers with named feature modules and a typed
  action registry. Mark each action as automated, manual helper, or unsupported
  using the existing rules matrix. A visible button must not imply complete
  rules automation when it only announces text or trusts a client calculation.
- Centralize committed-character publication. Rest helpers, DDB sync, and older
  feature macros should reconcile every live reference through a shared path,
  including combat state, version, visibility, and transformed characters.
- Expand behavior tests at boundaries: real database conflicts, mounted duplicate
  UI surfaces, delayed HTTP/socket ordering, two users, and two app processes.
  Mock-only tests should not be described as live multiplayer proof.
- Treat failed and partial actions as product states. Encounter Save/Delete and
  several older fetch paths still swallow errors. Preserve user work and offer
  safe retries with an explanation of what actually committed.

## Verification and Release Boundary

The regression tests added in this branch cover OAuth trust, admin email,
encoded asset requests, note revocation, limiter abuse, duplicate targeting,
snapshot/replay ordering, recovery rollback, DDB merge/recovery, and audio retry.
Final local gates on Node 24: all 157 test files / 2,084 tests pass (218 more
tests than the initial baseline); shared/client/server production build passes;
lint passes with zero warnings; full dependency audit reports zero vulnerabilities;
deployment script syntax and diff checks pass. Independent review caught and
corrected additional OAuth verification and music-transition regressions before
these gates. Music tests mount real React components with controlled Audio,
not a real browser.

The build still warns about a large dice worker chunk: approximately 2.89 MB
minified / 828 KB gzip. Measure first-use latency and memory on a modest phone;
keep 3D dice optional and lazy-loaded rather than hiding the build warning.

No production deployment, live player session, provider-login flow, or real
browser audio playback was performed during this code review. Before deploying,
review the auth rollout note and single-instance mitigation above. After deploy,
test: linked Google/Discord login; private map access; one target click with
Hero open; rapid room switches/reconnects; music start/mute/unmute; failed
encounter retry; rest and DDB sync; and the two-player combat flow.

The main checkout's 19 pre-existing deleted image files were left untouched.
Generated local Husky files are now ignored so they do not pollute source changes.
